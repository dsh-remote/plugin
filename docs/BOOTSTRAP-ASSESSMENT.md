# 自举迭代评估：免扫码重连 + appid 自适应配对

> 评估日期 2026-10-04。结论基于代码实读，每条都给了 `文件:行号`。
> 这份文档只做评估与设计，**尚未实施**。

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| dsh 重启后重扫的根因 | **不在协议，在主机自己会自毁**。修得掉，且不牺牲任何安全性 |
| 免扫码自动重连可行吗 | 可行。主机侧持久化 PSK 即可，**不需要新增任何协议帧** |
| appid 自适应配对可行吗 | **不可行**。appid 是公开常量，能当标识不能当凭据。这条路要放弃 |
| 自举还缺什么 | 5 项，其中 2 项是硬阻塞（见 §4） |

## 1. 根因：主机每次重连都在清空自己的会话

### 1.1 链路

`transport/relay.ts:280-287`：

```
case 'hello-ok': {
  this.generation += 1
  const dropped = this.conversations.closeBefore(this.generation)
  for (const id of dropped) this.options.onConversationGone(id)
  this.emitState('online')
  this.raw({ t: 'resync', sessionIds: this.conversations.ids() })
```

`generation` 是**主机进程内的自增计数器**（`relay.ts:87` 初始化为 0），不是中继的代次。
每次收到 `hello-ok` 就 +1，而 `closeBefore(generation)` 会删掉所有 `generation < 当前值` 的会话
（`core/keys.ts:119-128`）—— 于是**每次重连都是一次全清**。

配合 `PairingSlots` 是纯内存 `Map`（`core/keys.ts:203`）、PSK 只活在这里，
`resync` 发出的一定是空列表，中继照着删（`state.ts:212-226` `resync()`）。

手机侧：`error{unknown_session}` → `_forgetPairing()` → `needs-pair`（`core/client.js:276-277`）。
这是 F5 里客户端**唯一**被授权清配对的 code，绕不过去。

### 1.2 为什么说这是 bug 而不是设计

注释写的是「中继重启过：它手里的 convId 全没了，本地留着也只会解不开」（`relay.ts:282`）。
但中继重启时 `helloOkForHost` 只回 `{ hostId, protocol }`（`protocol/src/wire/outbound.ts:51-53`），
**不带任何代次信息**。主机无从判断中继是否重启过。

结论：`generation` 把「主机自己重启」误判成「中继重启」，清空是误伤。

对照两种场景：

| 场景 | 中继表 | 主机 PSK | 该不该清 |
|---|---|---|---|
| A 中继重启（+主机） | 已空 | 已丢 | 清是对的，本来就得重配 |
| B **只有主机重启（自举）** | 完好 | **可恢复** | 不该清，却跟着清了 |

场景 B 就是自举要解决的场景。

## 2. 免扫码自动重连：可行，不需新协议帧

### 2.1 为什么不用改协议

会话拓扑已经是 **1:1**（一部手机一条会话，见 `state.ts:151-153` 的 `leaveAll` 注释）。
手机侧 `installId` 与 `convId` 都持久化在 wx storage（`core/session-store.js:11-12`），
重启后用同一个 `clientId` 发 `hello`，中继原样保留（`state.ts:107-118`）。
**手机侧一个字都不用改。**

缺的只有一样：主机重启后还能算出同一份 `kC2H/kH2C`。

### 2.2 修法：把密钥簿落盘

`ConversationBook` 的键是 `convId`，值含 `kC2H`/`kH2C`/`psk`（`core/keys.ts:19-31`）——
落盘后 `closeBefore` 与 `pruneStale` 都能跨进程正常工作，语义不变。

落点：`~/.dsh/dsh-remote-control/conversations.json`，与 `host-id` 同一目录、
同样的 `0600` + `wx` 抢注 + 读不到就退化的纪律（照抄 `shell/host-id.ts:37-71` 的形状）。

**安全性没有牺牲**，理由是现有的威胁模型已经假定这个目录是可信的：

- `status.json` 现在就已经把**有效配对码 + PSK** 写在这个目录里（`shell/status.ts:11-12`
  的注释明确写了这件事，`index.ts:386-387` 的 `describeActivePairing` 真的返回 `psk`）；
- `host-id` 已经是这个目录里的持久凭据；
- 真正的边界「中继不可信」由**密钥从不上网**保证（`frames.ts:19` D1），
  落盘发生在主机本地，不改变这一点。

也就是说：**这个目录里今天就已经躺着 PSK 了**，把它从「每次重启换一把」变成「长期持有一把」
不新增攻击面，只是延长了同一份材料的生命周期。

### 2.3 必须同时修 generation（关键）

⚠️ **只做 2.2 不改 generation 等于没做**：落盘回来的会话会在下一次重连时
再次被 `closeBefore` 清掉，而且这次是「看起来配好了、下一帧就死」——比现在更难查。

正确做法：让中继在 `hello-ok` 里回一个**权威代次**（进程启动时生成一次、单调递增）。
主机收到后与自己落盘的代次比对，只在**真的变了**时清会话。

`hello-ok` 加字段不违反 F1（F1 冻结的是既有帧的**语义挪用**，加字段是兼容扩展；
小程序 `_onFrame` 的 `default` 分支会静默忽略不认识的字段）。

### 2.4 边界与代价

- 中继重启**仍然要重扫**。这是对的：中继表全空、PSK 也无法验证（它没有 PSK）。
  但可以把这条体验做好：主机检测到代次变了之后，**自动发一张新码**，
  手机端因为还存着旧 pairing 会撞 `unknown_session` —— 这一步仍然需要用户扫一次。
- 落盘文件成了新的敏感资产：拿到它 = 能解该主机所有历史会话的密文。
  需要配一个「导出/备份」纪律，且**不进 git**（加 `.gitignore` 断言）。
- `_prune` 的 `idleTtlMs` 语义要注意：落盘后它跨重启生效，
  「一天没收发就剪掉」会让长假期的手机在主机重启后被剪掉。
  自举场景下建议把落盘的那部分 TTL 放宽。

## 3. appid 自适应配对：不可行，建议放弃

### 3.1 事实

- appid 是**编译期常量**，`project.config.json:3` 明文写着 `wxfe76ed3135e010e3`；
- 小程序代码**从未调用** `getAccountInfoSync` / `wx.login` —— grep 全仓零命中；
- 即使去读，拿到的是「我自称是 wx…」——**声明，不是证明**。

### 3.2 致命的一点

**知道一个 appid 就能写一个同名小程序。** 攻击者不需要偷代码，写一个 appid 相同的壳就能声明同一个身份。
把 appid 当放行条件 = 把门钥匙的图案印在门上公开贴出。

对比现状：扫码这道门，密钥在二维码里（128 bit PSK）、有 TTL、一次性、
中继只见到 6 位码且**从没有过密钥**（D1）。用 appid 换掉它，是**降低**安全性，不是保持。

### 3.3 appid 适合放的位置

- **审计**：`status.json` 里带上 appid，排障时能一眼看出「哪台手机、哪个版本」；
- **命名空间**：多环境（dev/prod）用 appid 隔离，避免测试版误连生产主机。

一句话：**appid 是标识（identification），不是凭据（authentication）。**

如果确实想要「不同 appid 自动适配不同主机」这类体验，安全做法是**在 appid 之上再加一层**：
每个 appid 配一个独立的、由主机生成的接入码，落在主机侧配置里（0600），
而不是让 appid 本身成为通行证。但这已经是 §2 的「持久化密钥」问题，
appid 只是其中的一个索引键，不改变结论。

## 4. 自举还缺什么

按「阻塞自举 / 影响自举 / 体验」分级。

### 4.1 硬阻塞（不解决就自举不起来）

**① 免扫码重连（§2）** —— 就是本文的主问题。

**② 没有可回滚的部署路径。**
`install-to-profile.sh:73-77` 是 `rm -rf` + 覆盖拷贝，**没有备份上一版**。
自举意味着「改代码 → 装上去 → 可能起不来」。起不来时现在只能手动 `git checkout` 回去，
而此时手机已经连不上（问题①），人也可能不在机器旁边 —— **两个故障叠加就没有出路了**。
需要：装之前把旧 bundle 留一份，`status.json` 里报当前版本号，起不来时能一条命令退回。

**③ 自举会中断当前会话，且没有恢复路径。**
`install-to-profile.sh:152-163` 明写「必须重启 Harness」。自举必然重启，
正在跑的一轮输出、挂起的审批都会丢。需要明确：重启前是否给用户一个提示，
重启后能否续上（现在 `readSession` 缺失时是**明确拒绝、不返回空页**，见长期记忆）。

### 4.2 影响自举

**④ 版本与状态快照对不上。**
`status.json` 里没有插件版本号（`index.ts:327-372` 的 `state()` 全字段里没有）。
自举后无法从快照判断「现在跑的是哪一版」，排障时只能靠 mtime。

**⑤ token 两处一致性的脆弱性。**
`/etc/dsh-remote-control.env`(600) 与 `~/.dsh/profiles/desktop/cordis.patch.yml` 必须一致。
自举脚本如果误改其中一处，症状是「中继连不上」而非明确报错。

### 4.3 体验

**⑥ 自举期间的静默窗口。**
主机重启期间手机只会看到「连接已断开，正在重连…」。
自举可能几十秒到几分钟，用户会反复点重连。需要一个「主机正在更新」的信号。

## 5. 建议的落地顺序

1. **先做 `hello-ok` 带权威代次**（协议侧小改，`outbound.ts:51`）。
   单独这一步不会改变任何现有行为，但它是后面所有步骤的前提。
2. **再修 `relay.ts:281-283` 的 generation 语义**，改成比对代次而不是无条件自增。
   这一步做完，「主机重启丢会话」立刻变成「主机重启丢会话，但中继还在」
   —— 行为可控，且有 e2e 可测。
3. **然后做密钥簿落盘**（§2.2），含 `.gitignore` 断言与 TTL 放宽。
4. **最后做部署回滚**（4.1②），把 bundle 版本号写进 `status.json`。

**1 和 2 必须在同一个提交里**：只做 1 不做 2，主机仍然无条件自增；
只做 2 不做 1，主机拿不到权威代次。
