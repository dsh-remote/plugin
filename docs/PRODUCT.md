# 产品定义 — DSH Remote Control

> 这份文档回答一个问题：**在 `anywhere-labs`（Agents Anywhere + DSH Desktop）已经把"跨设备管 Agent"
> 做成一整套生态之后，我们凭什么还存在。**
> 回答的方式不是列功能表，而是先定死三条承诺，再从承诺推出界面与取舍。
>
> 写于 2026-10-04 凌晨。参考对象与实测对比见 §1；由承诺推出来的判据在 §3；
> 现在还不符合的地方列在 §5（那是待办，不是缺陷清单）。

## 1. 参考对象说清楚：它强在哪、代价是什么

`anywhere-labs/Agents-Anywhere`（1.4k★）+ `dsh-desktop`（29.8k★）里的 `dsh-bridge-next`
**就是一个 DSH cordis 插件**，peer 范围 `>=0.2.0-rc.1 <0.3.0-0`——和我们同一代宿主，
而且**随 DSH Desktop 打包**，在插件页里就叫"远程控制"。它的能力：iOS（App Store）/ Android /
Web / 桌面四端，设备-项目-会话三级管理 + 时间线，审批与输入请求，模型/权限/Agent 模式选择，
发文字/图片/文件，文件浏览与上传下载，远程 shell 与交互式终端。

它的代价写在自己的 README 里，两条：

1. **要账号 + 要服务端**：「远程连接需要 Agents Anywhere 账号和可访问的服务端」，
   自托管要跑 Docker，且「数据库 schema revision 单独编号」。
2. **数据过服务器**：「会话、时间线和附件等数据会按所用功能**经过或保存在** Agents Anywhere Server」。

所以我们独有的，恰恰是它结构上拿不走的三样东西。

## 2. 三条承诺（不可让步的部分）

**承诺一：零知识。** 载荷密钥只经配对二维码交给手机，**从不上网**；中继只见密文。
这条不是宣传语，它有闸门：`e2e/live-e2e.mjs` 的 ⑩/⑩b 逐帧检查"经中继的一切都不含明文"，
`e2e/run.mjs` 第 16 步对整条链做零知识帧审计。
**推论**：任何"把内容存到服务端 / 由服务端解析内容"的功能都不许做，
包括推送通知带正文、会话云同步、附件托管。

**承诺二：无账号、无常驻服务。** 没有注册、没有登录、没有 schema 迁移。
配对即授权，退出配对即结束。中继是**一个自包含单文件 + 一个 systemd 单元**。
**推论**：状态只能放在两端（宿主与手机）+ 中继的内存表里。
"换一台手机还能看到三个月前的会话"这种需求，我们直接放弃。

**承诺三：手机免安装。** 手机侧是微信小程序——打开即用，不是"下载 App 再登录"。
**推论**：手机是用来**处理**的，不是来**工作**的。小程序没有后台常驻、没有本地长会话存储，
把它做成 IDE 是在跟平台作对。

## 3. 由承诺推出的一条设计判据：**30 秒原则**

手机上一次使用应该是：**瞥一眼 → 决定一件事 → 走开**。
由此得到四条可判定的规则（评审时用它们砍需求，比"感觉不对"好用）：

1. **首屏必须是"有什么在等你"，不是"上次聊到哪儿"。** 挂起的审批/提问是唯一值得抢首屏的东西——
   它阻塞着远端一条正在跑的回合，而回合阻塞着用户的下班时间。
2. **每一眼都要能回答"我远程还管得住吗"。** 断链、没配对、密钥没交换，这三种"管不住"
   必须在桌面与手机上各有一处说得清的地方（不能只存在于日志里）。
3. **超时必须可见。** 一张审批卡 180 秒无操作就交还桌面，用户看不见那颗倒计时，
   就不知道自己按的按钮什么时候作废。
4. **"不行"要留得下原因。** 零知识架构下故障天然难自证（这一轮定位审批卡不弹，
   靠的是新加的四个字段 `approvalCalls` / `approvalLast` / `approvalAsked` / `approvalDecided`）。
   诊断面是产品面，不是运维的私事。
5. **一端答完，其他端那张卡当场作废。** 两端同时弹（插件不许改变宿主自己的行为），
   所以"决定已经下过了"这件事必须**立刻**传到每一端：桌面上点掉 → 手机上那张卡当场收；
   手机上点掉 → 桌面 composer 里那张卡当场收。留在屏幕上的废卡不只是难看，
   它会让人在一个已经关闭的请求上做写操作，还会让人以为"另一头没收到"而重复决定一次。
   实现与取证见伞仓 HANDOFF §9.15（两个方向用的是**不同**的机制，所以各有一条读数）。

## 4. 那些"看起来像缺陷"的取舍，是承诺的直接结果

| 现象 | 它不是 | 它是 |
|---|---|---|
| **同一时刻只允许配对一台** | "多设备管理没做" | 一把钥匙开一台机器。设备列表、权限分级、跨设备共享都是账号体系的附属品，我们没那个前提 |
| **没有文件浏览器 / 远程终端** | "功能不全" | 30 秒原则：手机上能做的只有"看一眼、决定一下、说一句"。要动文件请回工作台 |
| ~~**会话列表只读、不能删除/归档**~~ | ~~"交互缺失"~~ | **2026-10-07 部分放开：能归档，不能删除**（`cmd.archive_session` + mp 的行内「归档」）。当初那条理由是"手机不该改主机的项目结构"——**归档不改项目结构**，它把一条会话移进宿主的归档区，而那是**内核本来就有的能力**（`dsh-workspace` 的 `archiveSession`，真机上 55 条已归档会话就是它做的）。"删除"仍然不做：那是真删，删错了不可逆，而归档可以取消。⚠️ **归档 ≠ 停止**：内核会拒收仍在运行的会话（`WorkspaceActiveSessionError`），所以本产品**明确报"会话正在运行，不能归档"而绝不传 `stopActivity`**——插件不该改宿主自己的行为 |
| ~~**不能新建会话**~~ | ~~"交互缺失"~~ | **2026-10-05 已做**（`cmd.new_session` + mp 的「＋新建会话」）。当初的理由是"新建会话是坐下来再做的事"，而实测是：人在手机上想起一件该问的事，顺手开一条远比回到电脑前再开省事。**删除/归档仍不做**——那才是会改掉主机项目结构的那一半 |
| **不能切换模型** | "能力缺失" | 这一代宿主内核**只给读不给写**（取证：`status.json` 的 `modelFace = no-list+no-set`）。长一个点了没反应的下拉，比没有更坏 |

## 6. 明确不做（写下来是为了不用每次重新吵）

- 多设备/多用户/账号体系、跨设备会话同步（承诺二）。
- 任何需要服务端理解载荷内容的功能：搜索历史、云端摘要、推送带正文（承诺一）。
- 文件浏览、远程终端、IDE 式多面板（30 秒原则）。
  ~~图片消息~~ —— **2026-10-05 已做**（mp 选图 → `cmd.send_prompt.images` → 主机走宿主原生图片块，
  正文不出现路径）。它当年被列进"不做"是按"手机是用来处理的、不是工作的"推的，
  实测那条推论过头了：**问一句"这个报错是什么"配一张截图**，正是那 30 秒的一部分。
- 原生 iOS/Android 客户端：分发成本打不过"微信里已经装了"（承诺三）。
- **删除会话**。归档（移进内核自己的归档区、可取消）已经做了，删除没有——
  不可逆，而 30 秒原则下"清理列表"这件事的收益远小于误删的代价。
  真的要删，回工作台。

## 7. 与参考对象的关系，一句话

**它做"把工作台搬到别的设备上"，我们做"离开工作台时那 30 秒"。**
同一条协议层（`dsh-remote-wire`）如果哪天要接它的客户端，得先回答"载荷过不过服务器"——
那正是我们和它唯一不可调和的分歧。
