## 官方文档定案：`/api` 是分工的（Gateway vs API Proxy）

用户要求「优先 typertGateway（官方有文档），不要自己造轮子」。查官方
`@deepseek-ai/dsh-api-gateway/README.md` 后确认：

> the handler **dispatches claimed endpoints to Gateway and unclaimed endpoints to
> API Proxy**；只有 `extends TypertRemoteService` + `@Remote` 的方法才可经 Gateway 调用

- `SessionStore extends Service`（**不是** TypertRemoteService、无 `@Remote`）
  → `session.*` 走 **API Proxy**
- 它注册的 `lookup("session")` 是**参数解析器**，我原来把 lookup 名误当命名空间，
  才编出了 `session/list`
- 全仓库只有 `commands/list`、`tools/list`
- `dsh-web-app/cordis.patch.yml` 以 id `api-gateway` 挂载 `dsh-host-apiproxy`

**已改**：carrier 只认 `ctx.apiProxy`；**删掉全部自造的 typert 一元端点猜测**
（`callRc` / `session/list` / `session/prompt` / `session/cancel` / `$events/result`）；
Typert 只保留官方文档存在的 `$events` 命名流（`openWireStream`），且 `asGateway()`

### 我自己写的 bug：carrier 竞态（第二轮才修掉）

第一版 `decide()` 写成：

```ts
if (apiProxy) return start(gateway, apiProxy)
if (gateway) return start(gateway, null)   // ← 谁先到谁赢，等于没优先
```

结果重启后 `carrier: typert`（typertGateway 的 inject 先触发）。
**正确写法：只有 apiProxy 能立即启动；只有 typert 时交给宽限期定时器**
（`DRC_CARRIER_GRACE_MS`，默认 5000ms，测试设 10ms）。

**同时加了形状探针**：`bridge.describe()` 把内核服务**实际的顶层成员名**和
`hasSessionsList/hasMux/hasRespond` 写进 `status.json` 的 `bridge` 字段。
下次重启就能一眼看出 apiProxy 到底长什么样，不用再猜。

**测试踩坑**：`ctx.provide('dshRemoteControl')` 是**无条件**调用的，
所以不能用 `provided.dshRemoteControl === undefined` 判断「有没有启动」；
要断言 `api.createPairing()` 是否返回 null。

### 实测决定性事实：desktop 里没有 apiProxy

第二轮重启后探针显示 `apiProxy: null`，而 `typertGateway` 有
`wireStream / inProcessOperator / remoteEvents`。所以：

- `dsh-host-apiproxy` 虽在 `dsh-web-app` 补丁里挂载，**desktop 态没注册成 `apiProxy` 服务**
- `inProcessOperator` = `@deepseek-ai/dsh-client-connection` 的 `OperatorPeer`，
  文档注释说是 "Gateway's in-process carrier"，但不是文档化的 session 入口

**最终方案：同进程直接用平台服务**（carrier `services`）：
`ctx.sessions.list()` / `ctx.agents.get(id)?.status` /
`agent.followup(createUserMessage(...))`（动态 import `@deepseek-ai/dsh-llm`）/
`agent.abort()` / `ctx.on('session/event'…)`。
依据：官方 apiproxy 自己就是 `ctx.sessions.list()` + `agent.followup(message)`。
carrier 优先级 `services > apiProxy > typert`；`probeContext()` 把实际可见服务写进 status.json。

## 真机端到端跑通 —— 根因是我自己（waterfall 事件）+ 会话归档

**根因 1（决定性）**：`ctx.on()` 在 cordis 里注册的是**参与式**监听器；对 **waterfall**
事件，返回值会替换传给下一个监听器的值。插件曾订阅 `agent/request`（只观测），
返回 undefined 把 `proposedConfig` 冲成 undefined → `prepareRequest` 抛
`Cannot read properties of undefined (reading 'provider')`（app.asar 的 dsh-agent-loop:1186:22）
—— **进程内每个 turn 都崩，包括桌面 UI 手动发的**。这就是"重启了没用"。
修法：从订阅列表移除 + `WATERFALL_EVENTS` 黑名单（13 个）+ 两道回归测试。

**根因 2**：`@chaoset/session-archive` 把会话归档了；归档会话被宿主
`archived-session-gate` 在 `agent/pre-step` 拒掉 → `turn/end {reason:{kind:"blocked"}}`
（在任何模型调用之前）。修法：读 `ctx.workspaceRegistry.archivedSessionIds` 标 `archived`，
发送前 `unarchiveSession()`（`unarchiveOnPrompt`）。

**根因 3**：host-runtime 的 `flushDelta` 里 `if (!entry.text) return` 把 `turn/end`
的空文本 done 帧丢了 → 手机端永远转圈。修法：`if (!entry.text && !entry.done)`。

**最终验证**：真实内核 + 公网 wss：列表 11 个真实会话（6 archived）→ 发指令 → 
`assistant/message "ok"` → `turn/end completed` → 零知识 3 帧全密文。另跑了一次
工具型 prompt（bash），同样通过。

**环境限制**：本机所有会话 preset 都是 `danger-full-access` + `approval/policy: never`，
**永不弹审批卡**，审批/提问帧无法在此工作区实测。

**测试**：72 项 + e2e 9 步全绿。
