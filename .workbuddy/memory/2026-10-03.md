### 决定性取证：这一代内核换不了模型

`status.json` 的 `kernel.modelFace` = **`no-list+no-set via=currentSelection`**。
即 `agentDefaultModel` 上**只有 `currentSelection` 一个方法**，既列不出候选也写不进去。
`sessionController.commands` 上也只有 `ctx,agents,defaultCwd`，没有 `setModel`。

**踩过的坑（重要）**：第一版探测用 `Object.keys(agentDefaultModel)`，结果返回
**空数组**，差点得出"内核完全没有模型面"的假结论。原因是 cordis 服务对象的成员挂
在**原型链**上（accessor/proxy），而 `sessionController.commands` 是 own-property
形态所以能列出来。**同一个 `shapeOf` 在两个服务上一个有用一个没用**。
改成**逐名试调用**（`MODEL_FACE_METHODS` 清单 + `fn()` 探测）才拿到真相。
→ 判据/探测写完必须问一句「这个方法在这个对象上真的拿得到东西吗」。

### 四端改动

- **协议** `ev.model`：`model`（必填非空）、`provider`、`canSwitch`、`options[]`、`reason`。
  `canSwitch` **必须生产侧显式给**，不许手机从 `options` 有没有值去推断 ——
  "不能切"与"能切但清单为空"在手机上必须表现不同。工厂 `model()` 在不可切时
  **不下发 options**（空数组会让两种情况在手机上一回事）。
- **端口** `KernelPort.modelOptions()` 与 `modelSelection()` 分开：读当前值几乎每代都有，
  「能不能写」是代际差异最大的部分，合成一个返回值会让调用方分不清两种失败。
- **宿主** `broadcastModel()` 跟着 `pushSessions` 走（模型与防休眠都是全局状态，
  另开推送路径必然出现「会话更新了但模型没更新」的半同步）。
  **读不到就不发**，而不是发 `model: ''` —— 后者看起来像 bug。
  探针字段 `modelFace` / `commandsFace` / `agentModelFields` 留在 status.json 里取证。
- **mp** chat 页新增 `.modelbar`（顶栏之下、滚动区之外）。
  不可切时 `onModelTap` 弹 toast 说原因，**不**开面板（点了没反应比说清楚更糟）。
  审批卡加本地倒数 `deadlineAt`/`remainSec`，**先立刻算一次**再排下一秒，
  否则卡片挂满一秒才显示数字，而那正是用户盯着「允许/拒绝」看的时候。

### 「解配后 dsh 侧仍显示配对中」—— 三个独立缺陷叠加

用户报的现象。**根因全在主机侧，mp 的界面只是把它显示出来了**：

1. **`Conversation.clientIds` 只在 `open()` 初始化，此后从未登记也从未删 → 恒为空。**
   主机侧**根本没有**「几台手机连着」这个信息。登记点选在 `onEncrypted`
   （按帧里的 `clientId`），**不能只在 open() 记**：配对刚发生时成员表确实是空的，
   e2e 里不先发一帧，`pairedClients` 断言会因前提不成立而假红。
   摘除点选在 `peer-left`（D3「会话必须留着」不变 —— 会话留着 ≠ 这台手机还连着）。
2. **`emitState` 的 `clients` 写的是 `conversations.size`**，把会话数顶替成了手机数。
   解配重配会多一条会话 → 解完配对这个数**变大**，与「我的解配没生效」现象一致。
3. **`PairingSlots.prune()` 早就写好但从无调用方**（`grep -rn 'prune()'` 只命中定义），
   `pendingPairs` 只增不减（实测 5+）。接在 `relay?.pruneConversations()` 旁边。

mp 侧 `unpair()` 原来只本地清理 + 断线，**从不通知主机**。改走中继**已实现**的
`session-leave`（客户端分支）→ 转 `peer-left`。**不新增协议帧**（F1 冻结，
而中继那条路本来就在 —— 先查服务端有没有，比急着改协议省事得多）。

`socket.sendThenClose`：小程序 `SocketTask.send` 是异步投递的，
紧接 `close()` 会丢掉没进队列的帧。⚠️ 这个延迟在 Node 下**测不出来**（那里 send 同步），
所以不能拿「改小延迟会不会红」反证。

### 又踩了一次「反证没生效却当成判据无效」

第一次反证用 `perl -0pi` 多行替换去掉 `sendThenClose(...)`，结果 `grep -c session-leave`
返回 1 —— **替换根本没匹配上，文件没被破坏**。判据没红是因为破坏没生效，
不是判据不对。换成 Python 显式 `assert old in s` 再替换。
第二次反证破坏得太狠（整行变注释 → `if` 分支什么都不做 → socket 永不关），
e2e 直接**挂死** 5 分钟而不是变红。破坏要**最小**：只去掉要验的那一样。

**恢复时手滑把 `/tmp/sk.bak`（socket 的备份）拷到了 `client.js` 头上** ——
两条命令写在同一行 `cp A f1; cp A f2`，第二处用错了变量。
靠 `head -2` 核对文件头发现。**每次恢复后必须核对文件身份，不只看命令成功。**
